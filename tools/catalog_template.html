Why this exists

It is not really about the subjects. It is about tools for thinking through data, interfaces I would never have arrived at on my own, and finding out what a model builds when nobody narrows the brief.

I dispatch these by hand rather than on a schedule — a nightly habit, not a cron job. The brief is deliberately open: Claude chooses the subject, working from what it knows of my day job in research libraries and evidence synthesis, the things I build for fun, and whatever it feels like reaching for instead. Some of the best ones have had nothing to do with any of that.

Each build gets a real budget — a serious share of a usage window — with a standing instruction to spend part of it wrestling data out of somewhere awkward. A bold attempt that half works is a good outcome if it comes back with something learned. Several have.

As they arrive I keep notes on what actually landed: an interaction, a way of laying out numbers, a chart that taught me something. Not to bolt onto the next build, but as a growing palette to draw on when I am building something real. Feedback goes back in, so the builds and the brief keep sharpening each other.

A few are deliberately inward-facing — tooling that makes the next one better. This catalog is one of those: it and the publishing pipeline behind it were themselves a night's work.

How it is put together

In case it is useful — or in case it is me, six months from now, wondering how to add another one.

One repo per project

Every project is its own repository with its own Pages site, so it can be shared, forked or read on its own without dragging the rest of the shelf along. This catalog is an index over them and holds no project code.

The page is the deliverable

Each build ships as a single index.html with its data already inside it, usually as base64 typed arrays. The constraint comes from where these are first published, and it turns out to be a good one: no backend to rot, no key to expire, works offline forever.

Data is gathered at build time

A small pipeline pulls from public sources, reshapes and compresses, and splices the payload into a template. Those scripts live in each repo's src/. Raw downloads are deliberately not committed — the scripts refetch them.

Statistics are computed in the page

Almost nothing here is a precomputed number typed into HTML. Filters, aggregates, rankings and charts are recalculated in the browser from the shipped arrays, which is what lets the figures respond to whatever you filter to.

Rebuildable from scratch

Each repo carries a REBUILD.md written for a model with a shell and no other context: sources with exact URLs, the processing decisions and why, and a table of expected values to check the result against.

Licensing

Code is MIT. Data keeps whatever licence its source carries — mostly CC0 or US Government public domain, listed per dataset above. Where a source's redistribution terms are unclear, the project ships the derived page rather than the raw file.
