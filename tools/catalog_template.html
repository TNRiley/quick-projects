How this is put together

The workflow, in case it is useful — or in case you are me, six months from now, wondering how to add another one.

One repo per project

Every project is its own repository with its own GitHub Pages site, so it can be shared, forked or read on its own without dragging the rest of the shelf along. This catalog is just an index over them; it holds no project code.

The page is the deliverable

Each build ships as a single index.html with its data already inside it, usually as base64-encoded typed arrays. That constraint comes from where these are first published, and it turns out to be a good one: the page has no backend to rot, no API key to expire, and works offline forever.

Data is gathered at build time

A small pipeline pulls from public sources, reshapes and compresses, and splices the payload into a template. Those scripts live in each repo's src/ where they were kept. Raw downloads are deliberately not committed — the scripts refetch them.

Statistics are computed in the page

Almost nothing on these pages is a precomputed number typed into HTML. Filters, aggregates, rankings and charts are recalculated in the browser from the shipped arrays, which is what lets the figures respond to whatever you filter to.

Adding one

Drop a meta.json beside the new index.html, run tools/scaffold_project.py to generate the README, licence and first commit, then tools/build_catalog.py to regenerate this page. Nothing here is hand-maintained.

Licensing

Code is MIT. Data keeps whatever licence its source carries — mostly CC0 or US Government public domain, listed per dataset above. Where a source's redistribution terms are unclear, the project ships the derived page rather than the raw file.
